# VPS platform

Personal projects run self-hosted on a single VPS managed with Dokploy. AWS is
kept only for what a single server cannot do well: authoritative DNS, backup
storage, outbound mail, and each project's event and queue services.

This document records how the platform is organized and why. The runbook for
the shared services is in [`infra/vps/README.md`](../infra/vps/README.md); the
DNS stack is described in [`infra/aws/README.md`](../infra/aws/README.md#dns).

## Decisions

| Topic             | Decision                                                                                                                                                                                                                                                                                                                                        |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hosting           | Hostinger KVM 2 (2 vCPU, 8 GB RAM, 100 GB NVMe) in São Paulo, 24-month prepaid term, auto-renewal off. It can be upgraded in place to KVM 4 from hPanel. Compare providers about two months before the term ends.                                                                                                                               |
| OS                | Ubuntu 24.04 LTS, plain image. Hostinger's Docker Manager and Monarx add-ons are not used.                                                                                                                                                                                                                                                      |
| Deploys           | Dokploy. Every application service is a Dokploy **Compose** service that reads its `compose.yaml` from Git; only secrets live in Dokploy. Compose mode, not Swarm Stack, so `depends_on: condition: service_completed_successfully` works for one-shot jobs such as migrations. PostgreSQL is the exception: it uses Dokploy's built-in Database service, for its managed backups. |
| Images            | Built in GitHub Actions and pushed to GHCR; CI then deploys the service through the Dokploy API (`compose.deploy`) with a key of a Dokploy member limited to that project. Deploy webhooks are not used: they refuse while autodeploy is off and expect GitHub push headers. Nothing is built on the VPS.                                                                                                                                                                                                                  |
| Repositories      | Anything used by more than one project lives in this repository, along with personal apps. Anything used by one project lives in that project's repository: its app, Dockerfiles, compose file, migrations and AWS resources.                                                                                                          |
| Dokploy projects  | `platform`: services other projects depend on (PostgreSQL, Keycloak, later monitoring and WireGuard). `personal`: standalone personal apps (TeamSpeak, addy.io, Vaultwarden, Filestash). One more Dokploy project per project repository (`investflow`, …). One environment, `production`, until a project needs `staging`.                     |
| PostgreSQL        | One shared PostgreSQL 17 instance, a Dokploy Database service; its internal host is generated by Dokploy and lives in each client's Dokploy environment, not in Git. **One database and one owner role per project**, created by hand with the superuser using this repository's script. Projects run their own migrations with their own role. No external port. |
| Keycloak          | One shared Keycloak 26 instance, **one realm per project**. Realms, clients and users are configured by hand in the admin console; there are no realm files or configuration tooling in production. Production mode, capped heap, `KC_CACHE=local`, container memory limit.                                                                     |
| Keycloak exposure | The whole `auth.diogo-nb.com.br` host is routed publicly through Dokploy's Domains tab, including the admin console. Admin accounts in `master` require OTP, and brute-force detection is on. |
| Shared network    | Dokploy's `dokploy-network`. PostgreSQL is reachable on it by its internal host; project containers that need it join it. Projects reach Keycloak through its public hostname, since tokens carry it as `iss`. |
| Websites          | Served from the VPS: an nginx container per site on the same domain as its API, with Traefik routing `/` to the web container and `/api` to the API. S3 + CloudFront only for a site that must stay up when the VPS is down.                                                                                                                    |
| AWS               | The only cloud provider. Route 53 (zone `diogo-nb.com.br`), S3 for backups, SES for addy.io's outbound mail (Hostinger caps outbound mail at 5 messages per minute), and each project's EventBridge and SQS in `sa-east-1`. One IAM user per project, scoped to its own resources.                                                              |
| DNS               | Route 53 stays authoritative, managed by CDK in `PersonalPlatformDnsStack`, which owns the zone. `vps.diogo-nb.com.br` is the only record holding the server address; every service name is an alias record to it, so changing servers changes one value.                                                                                       |
| TLS               | Traefik obtains and renews Let's Encrypt certificates through the HTTP challenge on port 80. A hostname must resolve to the VPS before its service is deployed.                                                                                                                                                                                 |
| Memory            | Every container has a memory limit. Node apps set `--max-old-space-size` below it; Keycloak sets `JAVA_OPTS_KC_HEAP`.                                                                                                                                                                                                                           |

Domains in use: `auth.diogo-nb.com.br` (Keycloak), `dokploy.diogo-nb.com.br`
(Dokploy panel), `investflow.diogo-nb.com.br` (InvestFlow).

## Memory budget

The KVM 2 plan has 7.8 GiB usable. Figures were measured locally unless marked
otherwise.

| Service                              | Limit   | Typical use                           |
| ------------------------------------ | ------- | ------------------------------------- |
| OS + Docker + Dokploy + Traefik      | —       | ~1.5 GB (reported)                    |
| PostgreSQL                           | 1 GiB   | ~0.07–0.3 GB                          |
| Keycloak (heap ≤ 384 MiB)            | 768 MiB | ~490 MiB after startup                |
| NestJS API (heap 256 MB)             | 384 MB  | ~170 MB idle                          |
| Web (nginx)                          | 32 MB   | ~10 MB                                |
| TeamSpeak 6                          | 256 MB  | ~150 MB                               |
| addy.io + MariaDB + Redis, Rspamd on | 512 MB  | ~410 MB                               |
| **Core total**                       |         | **~3.7 GB, about half the host free** |

Keycloak's image sets `-XX:InitialRAMPercentage=50 -XX:MaxRAMPercentage=70`.
Without an explicit heap and container limit it can grow to about 70% of the
host; uncapped, it passed 900 MB in local tests.

## Adding a project

A project that uses the shared services needs:

1. A database and owner role, created with
   `infra/vps/postgres/create-project.sql` (see the runbook).
2. Its Postgres-facing containers on `dokploy-network`, with unique service
   names, connecting to the database's internal host on port 5432 with an explicit pool size
   (see the runbook). `max_connections` (100) is shared; Keycloak uses up to 20.
3. A Keycloak realm created by hand, with issuer
   `https://auth.diogo-nb.com.br/realms/<realm>`.
4. Its hostname added to `vpsServiceNames` in `infra/aws/dns/stack.go`.
5. A Dokploy project with its own Compose services, deployed from its
   repository's compose file (InvestFlow: `infra/dokploy/compose.yaml`).

### InvestFlow

Requirements read from the InvestFlow repository (`docker-compose.yml`,
`.env.example`, `infra/local-kc/`, Prisma schema and migrations):

- **PostgreSQL:** database `investflow` owned by role `investflow`, no
  extensions. The API reads `DATABASE_URL` (Prisma 7 with the `pg` adapter).
  InvestFlow runs `prisma migrate deploy` itself, as a one-shot `migrate`
  service that `api` waits for.
- **Keycloak:** realm `investflow`, configured by hand as described below.
  The API validates tokens against the realm's public keys and requires
  `aud` to contain `investflow-api`; it never authenticates to Keycloak, so
  it needs no client secret. The realm export in InvestFlow's
  `infra/local-kc/realms/` is for local development only: it seeds the public
  account `investflow-dev` and must never be imported in production.
- **Network:** `investflow-migrate`, `investflow-api` and `investflow-web`
  join `dokploy-network`, the first two to reach PostgreSQL and the web
  container for Traefik.
- **Deployment:** planned in InvestFlow's
  `docs/implementation/planned/production-deployment.md`: the compose file,
  the release workflow, the production Keycloak URL and the AWS stack.

#### Production realm

The realm is maintained in the admin console. This is its intended
configuration; keep it in sync when changing the realm.

| Area | Setting |
|---|---|
| General | Require SSL: all requests |
| Login | User registration off, forgot password off and verify email off (no mail server yet), remember me off, login with email on |
| Password policy | Minimum length 12, maximum length 64, not username, not email |
| OTP | Not required; users may configure it for their own account |
| Sessions and tokens | Defaults: SSO session idle 30 minutes, max 10 hours, access token 5 minutes, no refresh token rotation |
| Brute force detection | Lockout temporarily after 5 failures |
| Events | User and admin events saved for 30 days, admin events without representations |

Clients:

- **`investflow-api`:** confidential, every flow disabled, no redirect URIs.
  It only exists as the access tokens' audience, so no token can be obtained
  as this client.
- **`investflow-web`:** public, standard flow only, PKCE `S256` required.
  Root URL `https://investflow.diogo-nb.com.br`, home URL with a trailing
  `/`. Valid redirect URIs `https://investflow.diogo-nb.com.br/*` (the app
  returns users to the page they were on), post-logout redirect URI and web
  origin exactly `https://investflow.diogo-nb.com.br`. Its dedicated scope
  holds an **Audience** mapper (`investflow-api-audience`, included client
  audience `investflow-api`, access token and introspection only). Client
  scopes kept: `basic`, `profile`, `email`, `web-origins`, `acr`; removed:
  `offline_access`, `roles`, `address`, `phone`, `organization`,
  `microprofile-jwt`.

A correct access token for a user (Clients → `investflow-web` → Client
scopes → Evaluate) has `aud` `investflow-api`, `iss`
`https://auth.diogo-nb.com.br/realms/investflow`, `azp` `investflow-web`, and
no `realm_access` or `resource_access`.

## Backlog

- **Dokploy panel exposure.** The panel is public so GitHub Actions can reach
  the Dokploy API. It controls the Docker socket, so a bug before
  authentication means host compromise, and the hostname is discoverable
  through certificate transparency logs. Route only the deploy API path publicly
  and keep the panel behind the SSH tunnel or WireGuard. Until then, keep
  Dokploy updated.
- **PostgreSQL backups.** None yet. Configure Dokploy's database backups: an
  S3 destination (with its own IAM user, scoped to one bucket prefix) and a
  daily schedule. Consider WAL archiving (WAL-G or pgBackRest) later.
- **Keycloak admin exposure.** The admin console is public. If that becomes a
  concern, route only `/realms/` and `/resources/` publicly and reach `/admin`
  through WireGuard or an SSH tunnel (`KC_HOSTNAME_ADMIN`). The admin console
  signs in through `/realms/master`, so that path must stay public.
- **WireGuard.** Private access to the Dokploy panel and admin consoles.
